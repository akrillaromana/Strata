## Итерация 054: RAM-диск R: = 54 GiB

Новый стандарт персонального AWE RAM-диска — **54 GiB** вместо 64 GiB. Все активные локальные запускатели создают `R:` через AIM с `-s 54G`; номинальный 54-GiB NTFS том принимается при размере `>=53 GiB`. Для Q8_0 safety reserve при проверке ёмкости уменьшен до 0.5 GiB, поскольку на машине владельца полный Q8 runtime фактически оставлял около 11 GiB свободно на прежнем 64-GiB R:. Уже подключённый 64-GiB диск намеренно не уменьшается автоматически: сначала его нужно один раз отключить обычным способом, после чего следующий запуск создаст 54 GiB.

## Итерация 027: исправления отказов MTP и CUDA BF16/Q8_0

Устранена порча глобальных KV-режимов после неудачной загрузки MTP, утечка pinned memory при ошибке CUDA-alias, двойное освобождение KV-арены после неуспешного fallback и повторная инициализация уже занятого MTP-экземпляра. Добавлен контроль `hits/top-k` и 32-битных размеров CUDA-пуска BF16/Q8_0 routed experts. Все восемь личных моделей и профили E:/R: не менялись; реальные GGUF/GPU не запускались. Подробности в `docs/reports/iteration-027/`.

## Итерация 026: защита SwiGLU Q8_1 от FP16 Infinity и переполнения CUDA индексов

Нативные MTP и сгруппированные MoE CUDA-маршруты больше не используют отдельную неограниченную квантизацию SwiGLU: масштаб и сумма Q8_1 ограничиваются допустимыми конечными FP16 значениями, коды int8 насыщаются. Проверка `n_in × ncols` отклоняет арифметическое переполнение перед запуском CUDA. Обновлены GPU parity сценарии для будущих испытаний. Все личные профили, восемь моделей и E:/R: пути без изменений. CPU/Python/JS пройдены; реальный CUDA запуск не проводился. См. `docs/reports/iteration-026/REPORT.md`.

## Итерация 023 — полный preflight native head и embedding

GGUF-шарды Q6_K/Q8_0 теперь структурно проверяются **всей семьёй** до загрузки native head, dense и эмбеддингов в GPU. Пропущенные output/embedding, отрицательные размеры, переполнение таблицы и token ID вне словаря отвергаются. Кодовые C++/Python/JS проверки приведены в `docs/reports/iteration-023/`. Это не подтверждённый CUDA-запуск и не законченная поддержка всех личных моделей.

## Итерация 021: целостность GGUF шардов для Q6_K/Q8_0

Нативный dense loader больше не допускает частичную семью Q6_K/Huihui Q8_0: `GgufModel` должен подтвердить все metadata/shard/tensor counts до CUDA memory upload. ## Экспериментальный CPU↔CUDA parity для Q8_0 (итерация 052)

`--pcie-frac` меняет, какие native-эксперты выполняются CPU и CUDA. В обычном режиме эти пути математически
эквивалентны, но округляют промежуточные значения немного по-разному, поэтому даже при `temperature=0` ответ
может разойтись после первого близкого выбора токена.

Итерация 052 добавляет opt-in режим `--expert-parity cuda` только для native Q8_0/Q8_0 экспертов. CPU и CUDA в
этом режиме используют одинаковый Q8_1-контракт активаций, одинаковый порядок float32 reduction и общий
детерминированный SwiGLU. На CPU точная целочисленная часть Q8 dot ускоряется AVX-512F/BW/DQ/VL, если этот
набор доступен; VNNI/VBMI для parity-пути не требуются. На процессорах без базового AVX-512 остаётся скалярный
корректностный fallback.

Режим намеренно не включён в пользовательский JSON автоматически. Сначала новая сборка должна пройти прямой
synthetic CPU↔CUDA тест `native_expert_parity --cuda-placement-parity-q8`, а затем реальный Q8_0 —
`TEST-PCIE-PARITY.ps1`. При провале прямого теста `BUILD-Q8-PARITY.bat` не устанавливает новый `strata.exe`.
Для Q6_K, Q4_K_XL, Huihui и IQ3_S режим пока fail-closed: их CPU/CUDA арифметика должна быть выровнена и
доказана отдельно.

## Web live PCIe/MTP tuning (iteration 055)

Web runtime tuning теперь считается применённым только после подтверждения самого `strata.exe`. Текущий engine объявляет `request_tune=2 live_tune=1`: Web `Apply` немедленно посылает engine-команду `TUNE`, которая меняет активный expert scheduler в RAM; каждый завершённый request дополнительно возвращает engine-ACK для `pcie_frac` и `spec_min_p`. Старый exe больше не маскируется серверным echo: Web отключает controls и требует однократную пересборку.

После обновления итерации 055 один раз выполните `BUILD-RUNTIME-TUNE-ENGINE.ps1`, перезапустите модель, затем `VERIFY-RUNTIME-TUNE.ps1`. Проверка отправляет PCIe 0.00 и 1.00 одной resident model и завершается PASS только когда оба значения реально подтверждены engine. CPU/CUDA parity — отдельная задача и этим build не включается.

## Web live PCIe и неизменяемые конфиги (итерация 056)

`PCIe frac` и `MTP/spec_min_p` в Web теперь имеют два уровня применения: кнопка Apply немедленно отправляет control-команду `TUNE` в уже загруженный `strata.exe`, а каждый Web-request дополнительно передаёт те же значения как request override. Engine подтверждает текущий scheduler через `TUNED ... pcie_num`; завершённый ответ показывает фактический `PCIe offload ... entries`. Перезапуск модели между тестами не нужен.

Постоянные model JSON в корне и `PERSONAL_START_E_ai_Strata-Q4-Fork` являются только входными файлами. Server/launcher/Web их не переписывают. `/config` доступен только для просмотра; POST запрещён. Runtime-файл создаётся отдельно в `logs/.../runtime-*.json`. Saved autotune применяется только при явном `"autotune": true` в пользовательском JSON.


## Windows launcher bootstrap (iteration 059)

В PowerShell 7 сценарии из текущего каталога запускаются с явным `./` / `.\`, например:

```powershell
.\START-Q4-K-XL.bat
```

Это правило PowerShell Command_Precedence, а не ошибка BAT. После фактического запуска launcher теперь до подготовки RAM-диска проверяет Python server dependencies. Если существующая `.venv` осталась от старой версии и не содержит, например, `jinja2`, зависимости автоматически восстанавливаются из pinned `requirements.txt`, после чего import-probe выполняется повторно.

Default 059: `pcie-frac=0.09`, `spec-min-p=0.9`, `parallel=2` (native `--batch 2`).
